# 组长个人 Worktree 实施区设计

## 1. 目标

组长在团队仓库之外的同级目录开展技术主线工作，保留完整 Git 修改记录，但不直接改动 `main`。实现经过自测、数据检查和人工复核后，通过 Pull Request 合并到团队主分支。

## 2. Git 与目录关系

```text
D:\desktop\stu\铁信实习\
├─ railway-pdf-knowledge-graph\
│  └─ main 分支，团队稳定版本
└─ railway-pdf-knowledge-graph-leader\
   └─ feature/leader-implementation 分支，组长个人实施区
```

两个目录共享同一 Git 对象库和远程仓库，但拥有独立工作目录和检出分支。个人区不是仓库副本，不需要人工复制 `.git`，也不在主目录中切换分支。

## 3. 个人工作范围

组长负责以下技术主线：

- 项目任务拆分、接口约定和成员交付验收；
- 知识图谱 Schema 和数据质量规则；
- Neo4j 环境、约束、导入和查询；
- OCR 到结构化数据的处理链路；
- 自然语言问答后端；
- 最小查询与图谱展示前端；
- AI 辅助抽取和问答的边界控制；
- 集成测试、演示环境和最终合并；
- 成员延期时接管影响主链路的数据任务。

## 4. 分支内目录

继续沿用团队仓库已经定义的目录，不另建一套重复工程：

- `docs/leader/`：个人实施计划、进度、决策和验收记录；
- `scripts/`：OCR、数据检查、Neo4j 导入和评测脚本；
- `backend/`：后端实现及测试；
- `frontend/`：前端实现及测试；
- `data/import/`：允许进入团队仓库的已复核数据；
- `data/evaluation/`：评测问题和结果格式；
- `tests/`：跨模块验证。

原始 PDF、DOCX、OCR 临时图片、`.env`、Neo4j 数据库、依赖目录和构建产物继续由团队 `.gitignore` 排除。个人临时笔记若不准备合并，放在仓库目录之外，不在分支中建立 `private-notes/`。

## 5. 实施顺序

1. 固定开发环境、数据接口和最小样例；
2. 用 5 个实体和 5 条关系完成 Neo4j 导入查询闭环；
3. 建立 CSV 字段、ID、状态、引用完整性和证据检查；
4. 扩展到课程要求的数据规模和四类 Cypher 查询；
5. 完成后端问答闭环，答案必须返回证据；
6. 完成最小前端和图谱展示；
7. 建立 10 至 15 道评测题并执行集成验收；
8. 整理 Pull Request，复核后合并 `main`。

高风险工作优先验证：Neo4j 是否可用、扫描 PDF 的 OCR 质量、自然语言问题能否稳定映射到受控查询。前端视觉完善排在数据和问答闭环之后。

## 6. 提交与合并规则

- 每完成一个可独立验证的增量进行一次原子提交；
- 提交前运行仓库结构检查、对应测试和敏感文件检查；
- `feature/leader-implementation` 不直接强制推送覆盖历史；
- 未验证的实验代码可以留在本地分支，但不得合并到 `main`；
- 数据修改必须附带页码和原文证据，并由另一名成员复核；
- 合并前从 `origin/main` 获取最新变化，在个人分支解决冲突并重新测试；
- 通过 Pull Request 合并，不在 `main` 目录执行手工复制式合并。

## 7. 完成标准

个人主线达到以下条件后才可请求最终合并：

- 仓库结构检查通过；
- 数据满足课程数量和证据要求；
- Neo4j 可重复完成初始化和导入；
- 四类查询均有可验证结果；
- 后端返回答案、证据和明确错误信息；
- 前端可以完成最小问答流程；
- 10 至 15 道评测题有结果记录；
- README、运行步骤和演示步骤与当前代码一致；
- Pull Request 不包含原始课程文档、密钥、本地数据库或无关实验产物。

## 8. 当前不确定项

后端框架、前端框架、OCR 工具和大模型接口尚未锁定。实施计划先安排小型技术验证，根据本机可用环境和验证结果作出决定，并将决定记录在 `docs/leader/decision-log.md`。
